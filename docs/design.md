# Design notes

These are the decisions behind the code, in short. Comments in the code point at them as "decision 001" and so on. You will also see tags like GOAL16 or GOAL21 in comments: those are the milestones of the private project this came from, kept so the history of a piece of code still reads in order.

## 001 Architecture

One Python package, SQLite in WAL mode, and a standard library HTTP server. No framework and no build step for the UI, which is plain ES modules served from `job_hunt_agent/static/`. Dependencies are three libraries (python-docx, PyYAML, openpyxl) plus the optional `anthropic` SDK. Everything personal lives in an app home outside the repo (`~/.job-hunt-agent/`), and the shipped company registry in `config/` can be overridden by a file of the same name in the home.

## 002 Worth score

Two numbers per job. Match is how well your best resume fits: experience, hard skills, industry and title. Priority (0 to 100) is what to apply to first: fit 35%, freshness 30%, real-requisition signals 20% (a named team, posted pay, a requisition id) and seniority 15%, then multiplied down for reposts, evergreen talent-pool postings, non-US locations and languages you don't have. 70 and up means apply today.

Freshness is about the posting, not the scrape. A job that was taken down and reposted with a new date is chained to the original, so it does not look new.

## 005 Coverage

The registry has two layers: `config/companies.yaml` (curated, about 400 boards, wins every conflict) and `config/companies.discovered.yaml` (generated by `job-hunt-agent discover`). Discovery reads the Common Crawl URL index for Greenhouse, Lever, Ashby and Workday boards, adds S&P 500 Workday tenants found through their robots.txt, and only admits a board that has a US job posted in the last 60 days.

Boards are tiered by how often they post matching roles: tier 1 every 30 minutes, tier 2 every 4 hours, tier 3 daily. Each vendor (and each Workday data center) is its own rate bucket with its own queue, requests are conditional (a 304 costs nothing), and a host that answers 403 or 429 three times in a row is paused. robots.txt is checked on every request, with RFC 9309 matching.

## 006 and 008 Google Sheets and Drive

The app syncs with the tracker sheet you already have. It never creates a sheet, a tab or a visible column: it adds one hidden key column so rows can be sorted and moved freely, matches your columns by their header text, and writes only the cells that changed, so your formatting and dropdowns stay. Sheet edits come back by polling every few minutes. When both sides changed the same cell, the later edit wins and the conflict is logged. Rows are never deleted on either side.

OAuth is the installed-app flow with PKCE and a loopback redirect, using only urllib. Each user brings their own OAuth client because an open-source app cannot share one. Scopes are `spreadsheets` and `drive.file`, plus `gmail.readonly` for email reading, which is a separate token so disconnecting one never touches the other.

## 007 Keywords

Only hard skills count: tools, languages, frameworks, cloud services and methods, from a curated lexicon (`config/lexicon.yaml`) with aliases. A keyword's weight comes from how often the job mentions it and whether it sits under requirements or nice-to-have. Generic English words that are also tool names (Spark, Ray, Go, R) only count when written as part of a list, so "cost optimization" or "X-ray" never match.

## 009 and 010 ATS vendor profiles and models

For 15 vendors, `config/ats_profiles.yaml` holds what each vendor's own documentation says about resumes: parsing, file types, keyword search versus AI matching, knockout questions. Every line cites its source; anything undocumented is shown as "not publicly documented". Each vendor also has a small scoring model built only from those facts: literal keyword search where the vendor documents it, related-skill credit only where the vendor documents semantic matching. The numbers that are ours (weights, the 0.5 related credit) are shown on each vendor's "How this is computed" page. It is an estimate, and the UI says so.

## 011 and 014 More vendors and the gaps

Eightfold, Phenom, iCIMS career sites, Workable and a dozen smaller systems (BambooHR, Rippling, Gem, Recruitee and others) are fetched too. Google, Apple, Meta, Tesla, Uber and classic Taleo, SuccessFactors and Avature portals are not, because they have no public JSON feed, or their robots.txt or terms do not allow it.

## 012 Contact sources

Free sources first: names written in the job post, then the company's team page. Apollo (company and its top people) and Hunter (emails at a domain) run only on a click, show the credit cost before the call, are capped per day, and cache every answer so nothing is paid for twice. Phone numbers are never stored. Outreach is text only: the app never sends email or messages.

## 013 UI performance

The startup JavaScript has a size budget enforced by a test (120 KB uncompressed), and everything else loads lazily. The feed is ranked once and kept, with a fingerprint of everything that could change it, so switching tabs or filters does not re-rank thousands of jobs.

## Resume tailoring

The built-in tailor (`job_hunt_agent/tailor.py`) answers the same small JSON API a separate resume service would, so the queue, chips and side panel work the same with either. Claude gets the base resume and the job description with one rule: reword, reorder and emphasize, but never add an employer, title, date, number or skill. The answer is then forced back into the base resume's shape before anything is saved.

## Email reading

Python rules first drop alerts, newsletters and codes. Claude then reads the remaining emails in batches and answers in a fixed JSON shape: the kind of email, which application it is about, and how sure it is. A status changes only on a confident answer that matches exactly one application. Only the sender, subject, date, a short snippet and Claude's one-sentence reason are kept.
